## 1. 目标业务闭环

### 1.1 四层结构（自上而下驱动）

| 层 | 回答什么问题 | 关键产物 |
|---|---|---|
| ① 编制与能力 | 谁有资格上什么班 | 岗位 · 能级(N0-N4) · 资质 · 排班单元 · 班次字典 · 人力配置标准 |
| ② 需求测算 | 今天要多少人、什么能级、哪个时段 | 门诊←出诊计划；住院←在院患者 × 护理等级 |
| ③ 排班落地 | 谁、哪天、什么班、在哪个单元 | 三条业务线 + 共享出勤底座 |
| ④ 执行与回填 | 人真来了吗、差在哪、怎么校准 | 实际出勤 vs 计划 · 工时归集 · 差异归因 |

### 1.2 闭环四步

```
需求测算 → 排班生成 → 执行与考勤 → 差异归因 →（回头校准需求与标准）→ 需求测算
```

**闭环靠最后一步"差异归因"转起来。** 前三步做得再漂亮，没有第 4 步就是单向流水线，标准永远校准不了。

### 1.3 门诊与住院怎么咬合（重要，别再加外键）

- 门诊需求源 = **出诊计划本身**（哪些医生 × 哪间诊室 × 哪个午别）
- 住院需求源 = **在院患者 × 护理等级**
- 两条链**不在表层面咬合**，只在下游共享**人力池 + 出勤底座**处汇合（同一人同一时间只能在一处，互斥在底座判）

> ⚠ 结论：`biz_schedule` 与 `biz_nurse_schedule` **不需要互相加外键**。脱节的根因不是"两张表没关联"，是**中间没有需求层**。

**实际落地的派生口径**（sql/212 + `BizStaffDemandMapper`，两边逐字对齐）：

```
需求 = MAX(业务派生, 该单元核定的下限, 1)

住院护理：业务派生 = CEIL(Σ(在院患者 × 护理等级工时) ÷ 8h)
          等级工时（h/患者日）：特级 6.0 / 一级 3.5 / 二级 1.7 / 三级 0.6
门诊护理：业务派生 = 分诊 1 人 + 跟诊 CEIL(出诊医生数 ÷ 2)
门诊医生：业务派生 = 当日出诊医生数
```

**为什么必须取 MAX**（这是 P2 最重要的一条纠正）：病区护理不是纯按患者数配的。
一个病区哪怕只剩 1 个患者，白班/前夜/后夜三班也得有人顶 —— 这是最低运营配置，与患者数无关。
只按患者算会得到「全科医学科病区 11 个患者 → 需求 3 人」，而同规模病区实际在岗 6 人、核定下限 5 人，
那需求层就是在骗人。下限取自 `biz_staff_plan_rule.min_staff`（sql/204/213），
需求层和人力标准在这一刻才真的咬在一起。

**三条边界**：
- **每个启用病区每天都有一条需求行**（主表是 `sys_ward` 不是 `biz_admission`）：只铺"今天有患者的病区"
  会让其余 38 个病区在缺口面板上整片空白，护士长切过去看到一片「—」只会以为系统坏了。
  0 患者时患者派生为 0，需求就等于核定下限（三班还得有人顶）；
- 只铺 `period_code=0`（全天）+ `shift_id=0`（不限班次）—— 护理排班现在按天排，按班次拆会把配对口径搞复杂；
- 住院按「当前在院快照」铺 14 天，**未做出入院预测**（写进 `calc_basis`）；
- 护士长手工改过的（`demand_source=3`）重算时**不覆盖**。

**验收**：给定某病区某日，能算出"需求 N 人 / 已排 M 人 / 缺口 N-M"；门诊同理；前端能看到缺口面板。|

**缺口视图**（需求 − 在岗）：

```sql
CREATE OR REPLACE VIEW v_staff_demand_gap AS
SELECT d.demand_date, d.org_type, d.org_id, d.org_name, d.period_code, d.shift_id,
       d.staff_type, d.required_count,
       COUNT(s.id) AS scheduled_count,
       d.required_count - COUNT(s.id) AS gap_count
  FROM biz_staff_demand d
  LEFT JOIN biz_staff_schedule s
         ON s.schedule_date = d.demand_date AND s.org_type = d.org_type
        AND s.org_id = d.org_id AND s.staff_type = d.staff_type
        AND s.duty_status = 1 AND s.del_flag = 0
        AND (d.shift_id = 0 OR s.shift_id = d.shift_id)
 WHERE d.del_flag = 0 AND d.status = 1
 GROUP BY d.id;
```

### 5.3 G-17 实际出勤表（落地版见 sql/214，此处留最初设计；差异以 214 为准）

落地版相对本设计的四点演进：

1. **唯一键收口到「人 × 日 × 单元 × 班次」**（本设计少 shift_id）：同一个人同一天
   可以跨单元支援、也可以同单元两个班，这三件事是不同的事实，不能被互相吃掉；
2. 补 `planned_minutes`（计划工时快照）与 `overtime_minutes`（超时部分）——
   工时归集要的不是"实际多少"，是"和计划差多少"；
3. 补 `confirm_status/confirm_by/confirm_time`（科室确认）与 `data_source`
   （人工登记/考勤机导入/系统判定）—— 没有确认链路的考勤数据不能进绩效；
4. 新增三个视图承接 G-18/G-19：
   `v_staff_worktime`（行级对照，diff_type 1~9 九档，**7-未回填与 6-缺勤必须分开**）、
   `v_staff_worktime_summary`（单元×日：计划/实到/缺勤/未回填/加班五个口径分列）、
   `v_staff_calibration_advice`（差异归因 → 编制校准建议，**"数据不足"是独立一档**，
   未回填超 30% 时禁止给出上调/核减结论）。

另：`biz_shift` 补 `late_grace_minutes`（迟到宽限）—— 判定参数存班次字典，
SQL 视图与 Java 判定读同一个数，不写死两份。
