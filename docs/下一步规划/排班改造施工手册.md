## 1. 现状盘点（探查结论）

### 1.1 三个排班域，一张事实底座表

| 业务域 | 前端页面 | 后端入口 | 存储表 | 说明 |
|---|---|---|---|---|
| 全院岗位排班（员工排班） | `StaffScheduleView` | `/system/staffSchedule` | `biz_schedule` | 排班事实的唯一载体（谁·哪天·哪个单元·什么班·出不出勤） |
| 病区护理排班 | `NurseScheduleView` | `/nursing/schedule` | `biz_schedule`（同表，`orgType=2 病区 + staffType=2 护理` 区分） | 与员工排班共用底座表，各自页面维护 |
| 门诊排班（出诊+号源） | `ScheduleView` | `/schedule` | `biz_clinic_source` | **挂在 `biz_schedule` 上**：`staff_schedule_id` 外键引用底座行 |

- `biz_schedule`：`dutyStatus`（1上班/2休息/3请假/4培训/5停班）、`publishStatus`、`clinicFlag`（是否出诊 0/1）、`scheduleSource`（1手工/2模板/3复制/4换班）、`orgType/orgId/deptId/shiftId/startTime/endTime/workMinutes`。
- `biz_clinic_source`：`staffScheduleId`（外键）、`status`（0停诊/1正常/2已满/3已过期，号源可用性）、`publishStatus`、`doctorId/roomId/shiftId/totalSource/availableSource/diagnosisFee/diagnosisTier/consultStatus`。
- 科室主档 `sys_department`：`outpatientAuditorId`（门诊审核人）、`nursingAuditorId`（护理审核人）、`scheduleAuditorId`（排班审核人）。前端 `DepartmentsEdit` 已有三个配置项。

### 1.2 统一发布态状态机（三域一致）

`PublishStatusEnum`：草稿(0) → 待审核(1) → 已发布(2) → 调班中(3) → 已变更(4)。
`isEffective` = 已发布/已变更才算正式生效（出号 / 计在岗 / 展示）。

### 1.3 已实现的联动（仅"门诊 → 员工"单向）

| 动作 | 实现位置 | 行为 |
|---|---|---|
| 门诊排班新增/修改 | `BizClinicSourceServiceImpl.addSchedule / updateSchedule` → `bindCoreSchedule` → `StaffScheduleService.ensureForClinic` | 在 `biz_schedule` 派生/复用一条出勤事实（`clinicFlag=1`、`dutyStatus=WORK`、`publishStatus` 跟随号源行），并在复用侧做冲突校验（同键不同出勤态拒绝、响应形态不放号拒绝） |
| 门诊审核发布 / 撤回 | `doAudit / recall` → `syncCoreSchedulePublish` | 号源行的发布态同步到派生事实，避免"号源已发布、人却不计在岗" |
| 门诊删除 / 换绑 | `deleteSchedule / updateSchedule` → `releaseCoreSchedule` | 若无其他号源引用该事实，则删除孤儿底座行 |

### 1.4 审核人机制（后端已存在）

- 员工排班：`submit / auditPublish / reject / recall / adjustStart / submitWeek / auditWeek / pendingApproval`；`assertScheduleAuditor`＝当前登录人须命中科室主档 `schedule_auditor_id`，系统管理员(10012)豁免。
- 护理排班：同 `biz_schedule`，`submit / auditPublish / submitWeek / auditWeek`。
- 门诊排班：`submit / auditPublish / recall / adjustStart / submitWeek / auditWeek`；`assertOutpatientAuditor`＝命中科室主档 `outpatient_auditor_id`，系统管理员(10012)与门诊办(10035)豁免。

### 1.5 前端审批中心现状

`ScheduleApproveView`（排班审批中心）只聚合"全院岗位 + 护理"的待审（调 `pendingApproval`），**没有门诊排班待审入口**；门诊排班审核只能进门诊排班页逐条/整周操作，且门诊排班**没有驳回（reject）能力**。

## 2. 问题诊断（直接回答三个疑问）

### Q1：先做门诊排班，还是先做员工排班？

**答案：先员工排班（底座），后门诊排班（挂载）。这是当前架构已经采用且正确的方向。**

事实依据：`biz_schedule` 是排班事实唯一载体（全院岗位/护理/值守共用），`biz_clinic_source` 是挂在底座上的出诊计划 + 号源池（`staff_schedule_id` 外键）。门诊排班创建时通过 `bindCoreSchedule` 派生底座行，而不是另起炉灶——"出诊计划不得自己决定一个人今天上不上班，只能借用已有事实"（`reuseOrSave` 注释原文）。这个方向是对的，**不需要重建**。

真正要补的不是顺序，而是两条缺口（见 Q3）与审批闭环（见 Q2）。

### Q2：排完班谁来审核？

**答案：机制已经存在，缺的是入口完整性和体验。**

- 谁审：科室主档配置的审核人——门诊排班审 `outpatient_auditor_id`、员工排班审 `schedule_auditor_id`、护理排班审 `nursing_auditor_id`；系统管理员与门诊办全局豁免。
- 在哪里配置：科室管理编辑弹框（`DepartmentsEdit`，已有"门诊审核人/护理审核人/排班审核人"三个下拉）。
- 缺口 A：门诊排班的待审**没有统一入口**（审批中心只有员工/护理），审核人必须进门诊排班页逐条/整周审核。
- 缺口 B：门诊排班**没有驳回（reject）**，审核人只能"撤回"（撤回是排班人的操作），无法驳回并留原因。

### Q3：员工排班和门诊排班"感觉没联动"？

**答案：后端"门诊 → 员工"单向联动已实现；"员工 → 门诊"反向联动缺失，且前端页面互相看不见。**

已实现：门诊增改/发布/撤回/删除会同步底座行（§1.3）。

缺失（本手册 P1 要补）：

| 场景 | 现状行为 | 后果 |
|---|---|---|
| 员工排班页删除一条被门诊引用的行（`clinicFlag=1`） | `StaffScheduleServiceImpl.deleteById` 物理删底座行 + 人力复核，**不查门诊引用** | 号源行变成孤儿引用（`staff_schedule_id` 指向不存在的行），挂着的号仍能继续挂/约 |
| 员工排班页换班/代班（涉及出诊医生） | `swap` 只做时间与岗位校验，**不处理门诊号源** | 出诊医生换人后号源仍挂原医生，患者约的与实际看的不是一个人 |
| 员工排班页把出诊行改成停班/请假 | `upsert/applyShift` 直接改出勤态，**不停门诊号源** | 号源显示正常、还能约，但人实际不在岗 |
| 门诊派生行的发布态被员工排班页动作修改 | 员工排班侧 `submit/recall/adjustStart` 可作用于 `clinicFlag=1` 行 | 与 `syncCoreSchedulePublish`（门诊侧驱动）互相覆盖，状态分叉 |

## 3. 改造目标与范围

### 本期实施（对应 Q2/Q3 的直接痛点）

- **P1 员工 → 门诊反向联动补齐**：底座行被门诊引用时，员工排班侧删除/换班/停班/发布态动作一律联动或拦截，消灭孤儿号源与状态分叉。
- **P2 门诊排班审批闭环**：审批中心增加门诊排班待审入口；后端补门诊 `reject`（驳回）能力。
- **P3 前端穿透标记**：员工排班页对"门诊出诊"行做来源标记与操作引导，让两个页面互相看得见。

### 本期不做（克制清单）

- 不做"员工排班页直接创建门诊号源"（挂载方向保持门诊主导，属架构既定决策）。
- 不做停班后的自动批量退号（已有 `batchCancel` 手工批量退号，本期联动仅做到"停诊 + 提示有在挂患者"）。
- 不动排班总览（`overviewWeek`）、班次字典、人力配置标准、值守（duty）等相邻模块。

## 4. 施工步骤

### P1 员工 → 门诊反向联动（后端 `his-ms-outpatient`）

**文件清单**：
1. `service/impl/StaffScheduleServiceImpl.java`
2. `mapper/BizClinicSourceMapper.java`（只读查询，可复用既有 Mapper 方法或新增计数方法）
3. `entity/BizClinicSource.java`（不必须改，仅确认字段）

**改动点**：

**① 注入与引用计数**（`StaffScheduleServiceImpl`）
- 注入 `BizClinicSourceMapper`（同模块，直接引用，**不引入循环依赖**——注意不要注入 `BizClinicSourceService`，会与现有 `bindCoreSchedule → ensureForClinic` 形成环）。
- 新增私有方法 `clinicRefCount(Long staffScheduleId)`：统计 `biz_clinic_source.staff_schedule_id = ? AND del_flag = 0` 的引用条数。

**② 删除拦截**（`deleteById`）
- 在物理删之前：`if (clinicRefCount(id) > 0) throw new BusinessException("该排班已挂 N 条门诊号源，请先在门诊排班页删除/停诊后再删员工排班");`

**③ 换班/代班拦截**（`swap`）
- 对 `from`/`to` 两条行：任一 `clinicFlag == 1` 且被门诊引用 → 抛异常"出诊相关排班不支持在员工排班页换班/代班，请到门诊排班页处理"。

**④ 出勤态变更联动停诊**（`upsert` 的既有"改态"路径）
- 读取旧行：若旧行 `clinicFlag=1` 且被门诊引用，且新 `dutyStatus` 非 `WORK`（停班/请假/培训/休息）：
  - 把引用号源的 `status` 置为停诊（0）（复用 `BizClinicSourceMapper` 批量 UPDATE，或调用既有 `updateStatus` 逐条）；
  - 若有在挂号（`usedSource > 0`），返回提示语"已停诊，仍有 N 条在挂号，请到门诊排班页批量退号"（沿用 `staffScheduleUpsert` 的"提示不拦"返回风格）。
- 反方向（新 `dutyStatus == WORK`）：不改号源状态（恢复正常需在门诊排班页显式操作，避免误放号）。

**⑤ 发布态动作隔离**（`submit / recall / adjustStart / submitWeek / auditWeek`）
- 对这些动作的目标行：若 `clinicFlag=1` 且被门诊引用 → 抛异常"该班由门诊排班管理，发布态由门诊审核发布驱动，请到门诊排班页操作"。
- 理由：`syncCoreSchedulePublish` 由门诊侧独占驱动，员工排班侧不得再改这条行的发布态，否则与门诊侧互相覆盖。

**验收点**：①删除被引用行被拒；②换班/代班被拒；③停班联动停诊并提示在挂数；④门诊派生的行在员工排班页点提交/撤回/调班被拒；⑤原有员工排班（非门诊行）全部流程不受影响。

### P4 员工排班页默认隐藏门诊出诊行（前端）

**背景**：标准 HIS 里医生出诊排班归科室排班员/门诊办统一维护，员工排班页面向医技药护行政岗位。为避免页面把"门诊出诊"派生行混进岗位排班视线，默认不展示出诊行，需要时再显式筛选。

## 6. 数据一致性要点

- **引用即所有权**：`biz_clinic_source.staff_schedule_id` 指向的行，其"出勤态/发布态/生命周期"归门诊侧管理；员工排班侧一律只读或引导。
- **孤儿防护**：P1 的引用计数同时用于删除拦截与释放判定，与既有 `releaseCoreSchedule`（门诊侧删除时清底座）互为对偶，保证不产生无主号源、不残留无主事实。
- **状态不双写**：发布态写入只允许一个驱动方（门诊侧 `syncCoreSchedulePublish`），员工排班侧对派生行不做发布态动作。
- **停诊不删号**：停班联动只置 `status=停诊`，不物理删号源行；有在挂号时提示走 `batchCancel` 退号，与既有停诊语义一致。
