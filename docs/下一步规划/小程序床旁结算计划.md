# 小程序床旁结算计划

> 状态：**只计划，不实现**。等老王拍板分期与凭据到位后再排期。
> 配套前提：护士站床旁结算（`feature/bedside-settlement-nurse`，`/charge/bedside/*`）已上线，本文只解决「患者/家属侧」那半圈。

## 1. 目标与边界

**目标**：病区护士在床旁亮码 → 患者/家属用**微信扫一扫**直接打开小程序床旁结算页 → 页内看清这笔出院账单（明细 + 医保拆分）→ 微信支付 → 钱货两讫，双方都不用离开病区/收费窗口。

**做什么**：

| 项 | 内容 |
|---|---|
| 床旁码新形态 | 护士站亮码增加「微信小程序码」档（现有聚合码保留兜底） |
| 患者侧新页面 | 小程序 `pages/bedside/bedside`：扫码进入 → 账单明细 → 支付 → 结果 |
| 支付单新业务类型 | `PayOrderBizTypeEnum` 增加 **4-出院结算**，复用既有支付单/到账回填链路 |
| 到账闭环 | 异步回调 + `syncFromChannel` 兜底 + 护士站既有 5s 轮询，三路到账口径一致 |

**不做什么（明确划界）**：

| 不做的 | 原因 |
|---|---|
| 小程序侧**出账/试算/作废账单** | 结算动作是财务动作，只能发生在护士站/收费台；患者端只对「已生成的账单」付款 |
| 小程序侧**退款** | 退费要走审核，不开放患者自助（`/miniapp/pay/refund` 保持业务线内部调用） |
| 预交金充值搬进床旁流程 | 预交金是独立资金流，小程序 `pages/deposit` 已有入口，不混入出院结算 |
| 配送/订餐 | 跨营养域，与支付解耦，另立需求 |

## 2. 现状盘点（代码实查，2026-10-24）

| 侧 | 已就位 | 缺口 |
|---|---|---|
| 护士站 | `/charge/bedside/` 8 端点（榜/试算/出账/结算单/出码/查单/模拟付/关码），类级 `nur:bedside:settle` + 病区门禁（`DeptScopeService` 写操作复核）；`qrCreate` 出聚合码 | 没有小程序码形态 |
| 小程序患者端 | `/miniapp/pay/pendingBills`（按登录态取**本人**待缴账单，**不筛 billType，已含出院账单**）；`createOrder` 双模式（桩直付 / 真收银台回 `payParams`）；`syncFromChannel` 兜底；`pages/deposit` 已有在院列表/余额/流水；`pages/payment` 待缴页在用 | 无床旁扫码页；`createOrder` 只认 bizType 1/2/3；无小程序码生成通道 |
| 微信侧 | `code2Session`（`WxLoginChannelService`） | **无 `access_token` 缓存、无 `wxacode.getUnlimited`**（全仓 grep 零命中）；JSAPI 真下单 + V3 回调验签未实现（`MiniPayServiceImpl` 微信通知通道明确报未接通） |

**关键复用点**：两条支付路径（聚合码 / 小程序）都落同一张 `biz_pay_order`，到账都走 `confirmPaid` 回填 → 写流水 → 账单置平。护士站轮询、DB 复算、欠费榜口径**不用改**，这是把方案做小的根本原因。

## 3. 关键设计决策

### 3.1 床旁码用小程序码，不用聚合码（推荐）

| 维度 | 聚合码（现状） | 小程序码（推荐） |
|---|---|---|
| 谁能扫 | 微信/支付宝/云闪付 | 只有微信 |
| 微信内体验 | 扫码打开外部 H5 收银台，微信对外部支付链接有拦截策略，**体验不可控** | 原生小程序页，账单明细 + 医保拆分 + 支付结果一体 |
| 患者身份 | 无（裸支付） | 登录态 → 可校验「这是本人的账单」 |
| 链路改动 | 已通（dev 桩） | 复用 `createOrder` JSAPI 通道 + 新建小程序码通道 |

结论：**床旁场景患者/家属几乎只用微信**，小程序码在体验与安全上都更优；支付宝/云闪付用户引导到收费台（码面旁印提示）。收费台聚合码口径不动（一码三通是收费台规格）。护士站 UI 文案「微信 / 支付宝 / 云闪付均可扫」随小程序码档位改为「微信扫一扫，打开小程序支付」。

落地方式：`qrCreate` 加 `codeType` 参数（1=聚合码 默认 / 2=小程序码），先不改默认值，UI 上加档位切换；聚合码作为小程序不可用时的兜底。

### 3.2 出账权在小程序外，患者端只付「本人账单」

- 小程序任何接口都**不接收 patientId 入参**，一律 `UserUtils.getCurrentUser().getPatientId()`（与 `/miniapp/pay/*` 现有范式一致）。
- 支付前服务端复核：账单存在 ∧ 未作废 ∧ 未付清 ∧ `bill.patientId == 当前登录患者`。不满足直接拒，**不让前端传什么就信什么**。
- scene 里只带 `billId`（雪花 19 位 < 32 字符限制），**不带金额、不带任何可篡改字段**；金额一律服务端按 billId 现算。

### 3.3 金额与展示口径

全部沿用收费域既有口径，小程序不自算：应缴 = `payable - paid`；医保三拆（统筹/个账/自付）取账单行汇总；试算结论文案由服务端给。小程序页只做展示与确认。

## 4. 端到端时序（P0 目标态）

```
护士站(床旁)                     后端                        小程序(患者)
   │  亮小程序码(codeType=2)      │                            │
   │─────────────────────────────>│  wxacode.getUnlimited     │
   │<─────────────────────────────│  scene=billId 的码图      │
   │  展示码 + 倒计时              │                            │
   │                              │     微信扫一扫，scene 带入  │
   │                              │<───────────────────────────│ onLoad(scene)
   │                              │  床旁账单详情(患者侧,校验本人)│
   │                              │───────────────────────────>│ 明细+三拆+应缴
   │                              │<───────────────────────────│ createOrder(bizType=4, billId)
   │                              │  建/复用支付单 → JSAPI 预下单 │
   │                              │───────────────────────────>│ payParams
   │                              │<───────────────────────────│ wx.requestPayment
   │                              │  支付回调/查单 → confirmPaid │
   │                              │  回填支付单+流水+账单置平     │
   │  轮询(现有5s)到账回显         │                            │  支付成功页+订阅消息
```

三路到账互备：异步回调（主）→ `syncFromChannel` 渠道查单（兜底）→ 护士站轮询（护士侧可见性）。任一路到账都写同一套账，不重复入账。

## 5. 数据与权限边界

| 动作 | 护士站 `/charge/bedside/*`（`nur:bedside:settle`） | 小程序 `/miniapp/*`（`PATIENT`） |
|---|---|---|
| 病区榜 / 试算 / 出账 | ✅ 唯一入口 | ❌ 无接口 |
| 亮码 | ✅ 聚合码 / 小程序码双档 | ❌ |
| 看账单明细 | ✅（含全费用行） | ✅ 仅本人未缴清账单 |
| 支付 | ❌（床旁不代收，患者自己扫） | ✅ `createOrder` bizType=4 |
| 关单/取消 | ✅ `qrClose` | ❌（患者放弃支付即走开，码过期自动关） |
| 退款 | 走收费台退费流程 | ❌ |
| 数据范围 | 岗位科室（`DeptScopeService`） | 登录患者本人（后续 P1 扩监护人绑定关系） |

## 6. 分期排期

| 期 | 内容 | 依赖 | 预估 |
|---|---|---|---|
| P0 | 小程序码通道（access_token 缓存 + getUnlimited）；患者侧床旁页；`bizType=4` 支付；护士站码档切换 + 文案；订阅消息；API+UI 双跑 E2E | 微信小程序已认证；**JSAPI 商户凭据**（商户号/APIv3 密钥/商户私钥证书，与聚合网关 Native 同一套） | 凭据到位后 1 个迭代 |
| P1 | 家属代付（`/patient/guardian` 绑定关系放行）；支付结果页与缴费记录打通（`myOrders`）；`pages/payment` 从旧 `pendingPage` 切到 `pendingBills` 统一口径 | P0 上线 | 1 个迭代 |
| P2 | 床旁码双模（小程序码 + 聚合 H5 兜底同码或双码）；住院日清单小程序化；出院带药配送联动（M2 剩余项） | P1 + 配送需求 | 另立 |

**阻塞项只有一个**：微信 JSAPI 真通道凭据（`MiniPayServiceImpl` 现明确「JSAPI 下单与 V3 验签解密均未实现，缺商户号/APIv3 密钥/商户私钥证书」）。dev 桩模式下 P0 全部功能可开发可自测（`createOrder` 桩模式直接置已支付），凭据只卡真实资金流。

## 7. 风险与未决问题

| 风险 | 应对 |
|---|---|
| 小程序码通道新建（access_token 缓存）踩微信限流 | token 按 2 小时缓存 + 失败重试一次；码图按 billId 缓存复用（与护士站「缓存复用→间隔闸→配额」三道闸同思路） |
| scene 被伪造/重放 | scene 只带 billId；服务端校验登录患者归属 + 账单状态；过期时刻服务端锚定 |
| 患者已出院/账单作废的竞态 | 支付前复核账单状态（复用 `isPendingBillStatus`） |
| 重复支付 | 同一 billId 待支付单复用（不重复建单）；回调幂等按支付单号 |
| 家属拿患者手机付 vs 本人付争议 | P0 只认本人；P1 监护人绑定关系 + 代付留痕 |
| 旧版微信扫小程序码的兼容性 | 基础库要求写进 P0 验收项 |

## 8. 验收口径（P0）

1. API E2E：患者登录态扫 scene → 床旁账单详情（别患者账单 403/拒付）→ `createOrder(bizType=4)` → 桩模式到账 → DB 复算（支付单 paid、流水合计、账单 status=3）→ 关单幂等。
2. UI E2E：小程序床旁页扫码进入 → 明细渲染 → 支付（桩）→ 成功页；全程无 console error。
3. 跨端：护士站亮小程序码 → 患者侧支付 → 护士站轮询到账回显（头部欠费/未付清归零，复用本轮修好的榜单同步逻辑）。
4. 越权：医生/无权限护士调 `/charge/bedside/*` 403；未登录/别患者调患者侧接口拒。
