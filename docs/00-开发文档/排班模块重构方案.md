# 排班模块重构方案

> 基于 2026-10-10 ~ 10-11 多轮代码 / 库表 / 权限核对。核心结论：**统一一张「排班表」作为事实源，门诊号源和护理班次作为它的两张扩展；门诊 / 住院只是 `org_type` 一个维度，不再分表。**

---

## 0. 结论摘要（给老王）

三张表不是「细节毛刺」，是**分类法层面切歪了**。方向（统一底座 + 分域）对，但 domain 表没瘦下来、维度重复定义、消费方读错表、表名还误导人。老王最新拍板的命名重构（排班表 / 门诊号源表 / 护理排班表）把根因又往前推了一步：**「岗位出勤」这个名字本身就是坑，它其实就是排班。**

### 0.1 认知纠偏：本方案纠正的老王几处误解（2026-10-11 老王要求"别顺着说，挑刺 + 整改"）

> 以下不是"老王说得对"，是把此前几处想错 / 说错的地方挑出来，方案按正确结论落。

1. **"再来一张住院排班表"是反模式，已否。** 老王曾主张"排班表 + 门诊号源表 + 住院排班表"三分。但"门诊 / 住院"正是我们诊断出的根因维度（它只该是排班表 `org_type` 一个字段），再按地点分表等于把根因固化。正确模型**没有"住院排班表"**——住院场景的排班就是排班表里 `org_type=病区` 的行。
2. **"护理排班表不止有护士、还有医技各种"是事实错误。** `biz_nurse_schedule` 是代码强制只收护士（`selectNurse` 校验），医技 / 收费 / 行政一个都进不去；它们真正待在底座 `biz_staff_schedule`。把"底座（全角色）"和"护理扩展（只护士）"混为一谈，正是反复警告的"藕断丝连"陷阱。
3. **"把岗位出勤改名排班表"不是结构整改，只是改名。** 字段冗余、双写、pickDutyStaff 读错表、doctor_id 泛化口子一个都没动。改名只解决"语义清楚"，不能当架构修复。
4. **"护理排班还有人力配置标准，不是有岗位人力标准了吗"混淆了作业层与配置层。** 排了谁（作业）vs 至少排几个（配置）必须共存，不是重复；真正重复的是已废弃的 `biz_nurse_schedule_rule` 鬼表（已并入统一 `biz_staff_plan_rule`），那张才是该删的——本次已删（见 1.2.5）。

### 0.2 表名命名重构已落地（2026-10-11）

老王原话"表名太迷惑"——`biz_staff_schedule` 看着像"岗位出勤"其实是排班主体，`biz_schedule` 看着像"排班"其实是门诊号源。已执行改名把根因在命名层收敛：

| 旧表名 | 新表名 | 语义 | 从表一并改 |
|---|---|---|---|
| `biz_staff_schedule` | **`biz_schedule`** | 排班表（统一事实源，全角色） | — |

## 1. 现状诊断

### 1.1 三张表真实职责（代码核实）

| 物理表 | 业务名 | 模块 | 权限点 | 真存什么 |
|---|---|---|---|---|
| `biz_clinic_source`（原 `biz_schedule`） | 门诊号源 | his-appoint | `org:schedule:*` | 医生出诊 + 号源 + 诊室 + 费用 |
| `biz_schedule`（原 `biz_staff_schedule`） | 排班表（底座·统一事实源） | his-system | `org:schedule:*` | 所有人出勤事实（脊梁） |
| `biz_nurse_schedule` | 护理排班 | ~~his-patient~~ | 护理域 | **已退役（2026-10-11 并入 `biz_schedule`，见 10.5）**；护理排班代码同日迁 his-appoint |

### 1.2 结构性病症（四条，非冗余细节）

1. **分类法平行**——底座已有 `staff_type`（医疗/护理）× `org_type`（门诊/住院）两个正交维度，domain 表又各重存一套：`biz_schedule` 重存 `staff_type`、`biz_nurse_schedule` 用 `unit_type` 覆盖门诊/住院。谁信谁的就乱。
2. **写入者分裂 + 断链**——护士权威记录只在 `biz_nurse_schedule`，但分诊查「当天在岗护士」却读 `biz_schedule`（`pickDutyStaff(NURSE)`，`BizQueueServiceImpl:1351`）。两表独立写、互不同步 → 护士排班 UI 录的护士，分诊看不到。这是真 bug。
3. **泛化口子污染号源表**——`biz_schedule.doctor_id` 被泛化成「排班人员ID」，护士/收费/医技能塞进去，号源被清零、`clinicFlag` 还硬打成 1「出诊」。号源表从此不纯。
4. **表名误导 + 边界窄**——`biz_staff_schedule` 叫「岗位出勤」让人误以为和排班是两回事；`biz_nurse_schedule` 强制只收护士（`selectNurse` 校验），护工/护理员等住院部护理辅助岗被排挤在护理排班之外（`StaffTypeEnum` 无此类）。

### 1.2.5 鬼表残留：`biz_nurse_schedule_rule`（与上面"双存储"同源）

- 曾有一张护理专属的 `biz_nurse_schedule_rule`（COMMENT='护理人力配置标准'，his-patient），与统一的 `biz_staff_plan_rule`（COMMENT='人力配置标准'，his-system，用 `staff_type`(1-6)+`org_type`(科室/病区/全院) 覆盖所有岗位）**功能重复**。
- **sql/206 已废弃前者**：DDL 有 `deprecated` 列（"1=已并入 biz_staff_plan_rule，sql/206 起只读，勿再写入"），`NurseScheduleServiceImpl` 当时停了写入。
- **但表 + `BizNurseScheduleRuleMapper` + `BizNurseScheduleRule` 实体未删**：全后端 grep 只有其自身定义，无任何 service 读写 → 是"只废写不废表"的鬼表。
- **清理已执行（2026-10-11）**：实体 `BizNurseScheduleRule.java`、Mapper `BizNurseScheduleRuleMapper.java` 已删除（确认无任何 service 读写，纯死代码）；仓库内建表 DDL、种子数据 `biz_nurse_schedule_rule.sql`、导入入口 `00_import_all.sql` 对应行、ER 图（relationships.csv / er-by-domain.md）引用均已移除；已上线库 `DROP TABLE` 实测成功（BEFORE 存在 → AFTER 不存在）。交付物：`docs/03-增量SQL变更/20261011_清理护理人力配置标准鬼表.sql`（幂等 DROP）。ER 图 `index.html` 为生成物，需重跑生成脚本刷新。

> 重要澄清：**"护理排班"（`biz_nurse_schedule`，作业层/实际排班）与"人力配置标准"（`biz_staff_plan_rule`，配置层/最低人数阈值）不是重复**——前者是"排了谁"，后者是"至少排几个"，排班存完后系统拿标准校验"够不够人"。标准 HIS 同样分配置层与作业层，不应合并。

### 1.3 越权隐患（权限层）

- 804 / 2935 / 2937 / 2938 四个菜单 `permission` 全是 `org:schedule:list`，子权限都是 `org:schedule:*` → 一个开关罩住门诊出诊 + 全院岗位出勤 + 人数配置。
- 初始化时护士长(role 10)同时持有 804/2935/2937/2938 → 跨域能操作门诊和全院出勤，与「护士长只排护士」冲突。
- 收口后库里护士长已移除这些菜单（仅保留护理排班），但**当前日常能操作门诊排班/岗位出勤的只剩超管**——角色体系缺「门诊办/医务科/科主任」类管理角色（见第 8 节待拍板 A）。

## 2. 命名重构（本次核心，老王拍板）

### 2.1 旧表名 → 新表名

| 旧物理表 | 旧业务名 | **新业务名** | 定位 |
|---|---|---|---|
| `biz_staff_schedule` | 岗位出勤 | **排班表** | 统一事实源（唯一） |
| `biz_schedule` | 门诊排班（号源） | **门诊号源表** | 排班表的「出诊扩展」 |
| `biz_nurse_schedule` | 病区护理排班 | **护理排班表** | 排班表的「护理扩展」（含门诊护士） |

> 改名的意义：**「岗位出勤」=「排班」**，不该两张表两套叫法；门诊号源是出诊才产号的衍生，单独抽表；护理班次是排班表里 `staff_type=护理` 那些行的扩展。

### 2.2 维度原则（不再分表的依据）

- **门诊 / 住院不是分表依据** → 是排班表里 `org_type` 一个维度（`org_type=门诊科室` / `org_type=病区`）。
- **医疗 / 护理不是分表依据** → 是排班表里 `staff_type` 一个维度（只在排班表定义一次）。
- 医生住院出勤、收费/医技出勤、护士班次 → **全部进「排班表」**，靠维度区分，不另起表。

### 2.3 「住院排班表」澄清（已定稿：不存在此表）

明确结论：**系统里没有、也不该有独立的「住院排班表」。** 老王曾按"门诊 / 住院"提议新增此表，但那正是被诊断出的根因反模式——地点维度只应存在于排班表 `org_type`，不该用来分表。住院场景的排班 = 排班表里 `org_type=病区` 的行；护理班次因为有门诊护士（`unit_type=2` 分诊/跟诊），独立抽成「护理排班表」而非「住院排班表」，否则会漏掉门诊护士。

### 2.4 角色落到哪张表（硬映射，防混淆）

> 核心铁律：**「排班表」是底座（全角色），「护理排班表」只装护士。** 医技/收费/行政/医生住院出勤都不进护理排班表，它们只是排班表里的裸出勤行。

| 角色（staff_type） | 在「排班表」 | 在「门诊号源表」 | 在「护理排班表」 |
|---|---|---|---|
| 医生(1) 出诊 | ✅ 出勤事实 | ✅ **产号源**（唯一出口） | ❌ |
| 医生(1) 住院出勤 | ✅ 裸出勤（clinic_flag=0） | ❌ | ❌ |
| 护士(2) | ✅ 出勤事实（必含） | ❌ | ✅ **专属扩展**（含门诊护士） |
| 医技(3) 检查/检验 | ✅ 裸出勤 | ❌（号源清零，不放号） | ❌ |
| 药学(4) | ✅ 裸出勤 | ❌ | ❌ |
| 收费(5) | ✅ 裸出勤 | ❌ | ❌ |
| 行政(6) | ✅ 裸出勤（业务极少） | ❌ | ❌ |

- **"各种角色"真正待的地方是「排班表」底座**，不是护理排班表。所以不需要为医技/收费单独建表——它们只是不带领域扩展的出勤行。
- 只有**护士**需要一个独立扩展表（护理组/能级/班次册/护理工时这些领域字段），所以才分出来「护理排班表」。
- 医生需要号源扩展，所以分出来「门诊号源表」。
- 医技/收费/行政/医生住院出勤 **三者都不需要领域扩展** → 直接落在排班表，无需再分表。

## 3. 目标表结构（DDL 草案方向）

### 3.1 排班表（原 `biz_staff_schedule`，改名 + 补注释）
保留现有脊梁列：`employee_id, staff_type, org_type, org_id, org_name, schedule_date, shift_id, start_time, end_time, duty_status（上班/休息/请假/培训/停班）, clinic_flag, work_minutes, template_id, attend_mode…`
→ 全系统唯一排班事实源。互斥（`assertNoOverlap`）在此层统一判定。

### 3.2 门诊号源表（原 `biz_schedule`，瘦身）
只留出诊扩展：`id, schedule_id(FK→排班表), total_source, used_source, available_source, added_source, room_id, room_name, regist_fee, diagnosis_fee, expert_fee, is_expert, schedule_type(上午/下午/全天), status(停诊/已满/已过期), consult_status(接诊中/暂停)`。
→ 脊梁字段（schedule_date/dept_id/doctor_id/shift_id/start_time…）**全部删除**，从排班表 JOIN 取。只医生产号（`staff_type=1`）。

### 3.3 护理排班表（原 `biz_nurse_schedule`，改名 + 明确扩展）
只留护理扩展：`id, schedule_id(FK→排班表), nursing_group_id, nursing_post_id, nurse_title, shift_book_id, assign_patient_group, work_hours, night_shift_count`。
→ 脊梁字段删除；`unit_type`（1病区/2门诊）**降级或删除**，门诊/住院从排班表 `org_type` 继承。

## 5. 权限域拆分（已连库执行，2026-10-11）

将笼统的 `org:schedule:*` 拆细，让角色与菜单一一对应（对齐标准 HIS）：
- `outpatient:schedule:*` —— 门诊排班 / 号源（菜单 804 + 按钮 2120/2121/2122）
- `staff:schedule:*` —— 岗位出勤（2935）+ 岗位人力标准（2937）+ 班次 / 出勤 / 需求接口
- `nursing:schedule:*` —— 护理排班（331，**本就独立，未动**）
- `schedule:overview:list` —— 排班总览（2938），只读聚合

→ 护士长看不到门诊、门诊办看不到护理，跨域越权根因消除。

**关键口径：权限域是三处联动**，改其中一处而不改另外两处 = 403 / 按钮消失。本次三点同改：
1. 库 `sys_menu.permission`（`20261011_排班权限域拆分与补管理角色.sql`，含铺底种子 `sys_menu.sql` 同步改，避免新环境重装退回旧域）；
2. 后端 `@PreAuthorize` —— `BizClinicSource*Controller`→outpatient、`Staff{Schedule,PlanRule,Demand,Attendance}Controller` + `ShiftController`→staff、`ScheduleOverviewController`→overview；
3. 前端 `v-perm` —— `ScheduleView.vue`→outpatient、`StaffScheduleView.vue` / `StaffPlanRuleView.vue`→staff。

> ⚠️ `menu_key`（`org.schedule` / `org:staffSchedule` 等）是**路由标识**，一律不动；改的只有 `permission` 列。
> 注意 20261010 收口用 `permission LIKE 'org:%'` 做过回收，所以拆分前门诊排班/岗位出勤/人力标准实际只剩超管能操作 —— 这正是待补角色（第 8 节 A）。

## 10. `biz_nurse_schedule` 是否还有存在价值（老王质疑「不知道还有啥用」，2026-10-11 论证）

**结论：它是 `biz_schedule` 的冗余降维副本，可以合并掉。不是"字段差不多"，是严格子集还更弱。**

### 10.1 逐列对比（权威出处：`BizNurseSchedule.java` / `BizSchedule.java` 实体 + DDL）

| `biz_nurse_schedule` 列 | 在 `biz_schedule` 里 |
|---|---|
| `ward_id` / `ward_name` | = `org_type`(2-病区) + `org_id`，换了个名字 |
| `unit_type`(1-病区 2-门诊科室) / `unit_id` | = 窄化版 `org_type` / `org_id` |
| `nurse_name` / `nurse_title` | = `employee_name`（职称可从员工表派生） |
| `schedule_status` | = `duty_status` |
| `shift_name` | JOIN `shift_id` 可得 |
| `schedule_date` / `week_day` / `employee_id` / `emp_code` / `dept_id` / `dept_name` / `shift_id` / `start_time` / `end_time` / `work_minutes` / `schedule_source` | 完全一致 |

而 `biz_schedule` **还多**出：`attend_mode`(坐班/听班/留院)、`clinic_flag`、`employee_post_id`、`template_id`。

**致命的是唯一键**：护理表是 `(employee_id, schedule_date)` —— 一个护士一天只能一条，**连早晚双班都表达不了**；底座是 `(employee_id, schedule_date, shift_id)`。护理专属能力（护理组 / 能级 APN / 派班）它一个都没落。

### 10.2 决定性证据：它早就依赖底座，只是又把数据抄了一遍

`NurseScheduleServiceImpl.syncDayAttendance`（446 行起）：每点一个护理格，先调
`staffScheduleService.replaceDayAttendance(...)` 往 `biz_schedule` 写一条**出勤事实**，再把底座行 id 回写到护理格的 `staff_schedule_id`。

也就是说：**护士的权威出勤早就在 `biz_schedule` 里了**，护理表只是按病区视角把同一件事重新铺了一遍列。
`staff_schedule_id` 这根"指路牌"恰恰说明它本该是纯依赖视图，结果做成了平行副本。

### 10.3 合并后的收益

- 三张表 → 两张：`biz_schedule`（全院出勤底座，含护士 = `staff_type=2` / 护工 = 7）+ `biz_clinic_source`（医生号源）。
- 顺手把 P1 的护士取值从「读两张表再合并」降为**单源读**，断链类 bug 的根因彻底消失。
- 护士支持多班次/天（唯一键放开）。

### 10.4 风险与工作量（所以单独排一轮，不跟权限变更混在一起改）

1. **跨模块写**：`his-patient` 的护士模块要写 `his-system` 拥有的 `biz_schedule` —— 要么走跨模块服务调用，要么裸 SQL；哪种都要先定口径（项目约定跨模块读用裸 SQL，写更敏感）。
2. **行为变更**：原 UI 强制"一人一天一格"，迁到底座后同一人同一天可有多条（多班次），矩阵的取格/聚合逻辑要按 `(人, 日)` 归并。
3. **数据迁移**：存量护理行要落成底座行，并处理已存在的 `staff_schedule_id` 对应关系，避免重复底座行。
4. **P1 要回改**：`NurseDutyReadMapper` 现在读 `biz_nurse_schedule`，合并后指向 `biz_schedule`（`staff_type IN (2,7)`）。
5. **消费方**：护理台账 / 月度工时 / 告警规则 / 前端 `NurseScheduleView.vue` 全部要回归验证。

→ **待老王点头后执行**，优先级建议排在 P3（domain 表瘦身）之前——先消掉这张副本表，再谈瘦 column 边界。
