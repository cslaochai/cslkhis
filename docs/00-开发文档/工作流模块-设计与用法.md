# 工作流模块（his-ms-workflow）设计与用法

> 定位：把「同一条链有多个入口复用」「要落人工闸/要回放」的流程从代码里搬到配置里。
> 单点生成、单入口的能力不用上流程，直接写一个方法。

## 1. 结构

```
his-ms-workflow
├── controller   FlowDefinitionController（定义配置） / FlowRuntimeController（运行）
├── entity       FlowDefinition / FlowNode / FlowSkip / FlowInstance / FlowTask / FlowHisTask
├── mapper       6 个 BaseMapper（CAS 用 @Update 条件更新）
├── service      FlowDefinitionService / FlowRuntimeService（+ impl）
├── support      FlowConditionEvaluator（变量读写 + 条件判断，不做脚本求值）
└── dto/vo
```

跨模块依赖只有一条：`his-core-spi` 的 `FlowAiGatewayService`（工作流 → AI）。
AI 侧实现在 `his-ms-ai/spi/FlowAiGatewayServiceImpl`，只注入 `AiExecutionService`，是叶子适配器。

## 2. 节点类型

| node_type | 含义 | 要不要人工 | 出口 |
|---|---|---|---|
| 0 | 开始 | 否 | 一条 PASS |
| 1 | 审批 | 是（建待办） | PASS |
| 2 | 结束 | — | 无 |
| 3 | 自动（AI/服务） | 否 | 一条 PASS |
| 4 | 网关（条件分支/AI 意图路由） | 否 | 多条 COND，最后一条写 `DEFAULT` |

审批节点的 `node_ratio`：`0`=或签（一个任务，谁处理都算过）、`100`=会签（每个候选一条任务，全过才算过）、`n`=票签 n%（`ceil(总条数*n/100)` 条通过即过）。
`permission_flag` 写法：`role:DOCTOR@@user:1001`，待办列表按当前登录人的生效角色/员工 ID 匹配。

## 3. AI 节点怎么配（关键）

自动节点不写 Java，只配三样：

| 字段 | 说明 |
|---|---|
| `ai_action` | `CAPABILITY`=调一次模板拿结果；`ROUTE`=意图路由 |
| `ai_template_name` | 提示词模板编码，对应 `sys_ai_prompt_template.template_code` 的生效版本 |
| `ai_capability_key` | 能力开关，默认 `flow_ai_node`；路由节点用 `flow_intent_route` |

执行链路：节点输入 JSON（`节点 ai_input_json` + 当前流程变量 `variables`）→ 模板渲染 `{{inputJson}}` → 模型 → 结构化 JSON → 挂到流程变量 `变量[node_code]`。

所以新增一个 AI 步骤 = 在「提示词管理」里加一个模板 + 在流程里加一个节点，**不改代码、不发版**。

模型输出约定：
- `CAPABILITY`：任意 JSON；带 `answer` 字段会被提升为顶层变量 `answer`（患者端直接取）
- `ROUTE`：`{"flowCode":"目标节点编码","confidence":0~1,"reason":"..."}`，编码必须落在候选清单里，自造编码丢弃

## 4. 条件表达式

只支持「变量路径 运算符 字面量」，不做 SpEL：

```
ROUTE.flowCode == 'ANSWER_REPORT'
AGE > 65
DEFAULT
```

变量路径按 `node_code` 取该节点输出，如 `AI_CHECK.issues`。

## 5. 两个示例流程（SQL 328 已铺）

**患者咨询分流（PATIENT_CONSULT）**

```
START → ROUTE(网关, ROUTE) ─┬─ flowCode=='ANSWER_REPORT'       → ANSWER_REPORT(自动) → END
                             ├─ flowCode=='ANSWER_REGISTRATION' → ANSWER_REGISTRATION(自动) → END
                             └─ DEFAULT                         → ANSWER_GENERAL(自动) → END
```

调用：

```json
POST /workflow/runtime/dispatch
{"text":"我上次的CT报告写肺结节，要不要紧","channel":"MINIAPP","bizType":"PATIENT_CONSULT"}
```

返回 `flowCode` / `instanceId` / `answer` / `routeReason`，小程序直接把 `answer` 渲染出来。

**病历内涵复核（EMR_QC_REVIEW）**

```
START → AI_CHECK(自动, flow-qc-inner-check) → REVIEW(审批, role:DOCTOR, 或签) → END
```

启动时把病历文本放进变量：`{"variableJson":"{\"recordText\":\"……\"}"}`，AI 出的问题清单落在 `AI_CHECK.issues`，质控员看待办确认。

## 7. 并发与一致性

- 待办处理：`UPDATE ... WHERE id=? AND task_status='PENDING'`，同一待办只能处理一次
- 节点推进：`UPDATE ... WHERE id=? AND node_code=旧 AND flow_status='RUNNING'`，两人同时推进只有一人成功
- 驳回/撤回：作废该实例全部 PENDING 待办，实例落 REJECTED / CANCELED
- 一次推进最多 20 步，配成环会直接报错，不会把请求拖死

## 8. 纪律（沿用 AI 能力口径）

1. AI 节点只产出建议/文案/问题清单，**不写业务库、不产生扣分、不改事实层**
2. 模型挂了：自动节点记降级轨迹后继续走（不阻塞流程）；路由节点落到 `DEFAULT` 分支
3. 意图识别拿不准就返回空编码，让患者补充描述，不猜
4. 金额、编码、状态机、分级这些唯一正确答案，一律代码算，不进 AI 节点

## 9. 前端与菜单

页面（`source/front/src/views/workflow/`）：

| 文件 | 作用 |
|---|---|
| `FlowDefinitionView.vue` | 流程定义列表：关键字/状态查询、分页、详情、发布、删除；新增/编辑只做跳转 |
| `FlowDesignerView.vue` | 拖拽画布设计器（`@vue-flow`）：左侧节点面板、中间画布、右侧属性面板、连线属性弹框、一键美化、保存草稿/保存并发布 |
| `WorkflowNode.vue` | 画布自定义节点：开始/结束正圆 78px、审批（`#1269B5`）、AI 自动（`#0E9488`）、意图识别/网关（`#B45309`），按类型显示审批人表达式、AI 动作、或签/会签/票签 |
| `FlowDefinitionDetail.vue` | 只读详情（节点 / 流转线） |
| `FlowTaskHandleEdit.vue` | 通过/驳回意见弹框（被统一待办页复用） |

设计器口径（照 CA 的 `WorkflowDesigner.vue` 移植，节点/流转线字段按本模块 DTO）：

- 入口：列表页「新增流程」→ `workflow/definition/designer`；「编辑」→ `workflow/definition/designer/:id`。设计器不进菜单，`guard` 靠 `/workflow/definition` 前缀放行。
- 拖拽：面板项 `dragstart` 写 `text/plain`，画布 `@drop` 用 `screenToFlowCoordinate` 算落点；新节点编码自动生成（开始固定 `START`、结束固定 `END`、其余 `N1/N2...`）。
- 连线：`onConnect` 拦自连与重复边；点连线弹框改 `skipType`（PASS/COND/REJECT），`COND` 才写 `conditionExpr`（表达式只支持「变量路径 运算符 字面量」，兜底分支写 `DEFAULT`）。
- 保存：坐标写 `coordinate = "x,y"`（`Math.round`），节点顺序写 `sortNo`，整图 upsert。**新建时 upsert 出参是裸 Long，19 位雪花 id 过 JSON 会丢精度，前端不拿它当主键**——改为按 `flowCode` 回查 `listPage` 拿字符串 id，再 `router.replace` 把 id 写回 URL。
- 已发布流程不再显示「保存草稿」：upsert 不会把已发布流程回退成草稿，草稿保存会对线上流程静默生效，所以已发布只留「保存并重新发布」（发布里 version+1）。
- 载入顺序：先 `nodes` 再 `nextTick` 后挂 `edges`，否则 `@vue-flow` 报 `Edge source or target is missing`。
- 一键美化：按流转拓扑分层，从左到右排（列内按 y 排序，gap 76/48），完事 `fitView`。

流程待办不单开页面：并入「门户→统一待办」（`views/todos/UnifiedTodoView.vue`），数据源 `GET /workflow/runtime/listMyTasks`（按当前登录岗位过滤）。「消息中心」（原 `sys_menu` 102）已彻底并入本页：331 起只查不办、333 侧栏 `is_visible=0`、334 把 29654 铺到全部角色；它的全量消息能力变成本页「数据范围 = 全部消息」那一档，门户下只剩统一待办一条待办入口。

### 9.1 统一待办（门户→统一待办，`views/todos/UnifiedTodoView.vue`）

一张列表看两处待办：消息待办（`sys_message`，`handle_status=0`）+ 流程待办（`biz_flow_task`，`PENDING`），加「来源」列区分，点行走各自处置（消息 → `MessageProcessDialog`，流程 → `FlowTaskHandleEdit`）。行内动作仍认既有两个按钮码：`portal:messages:edit`、`workflow:task:handle`。

**与消息中心（102）的关系**：102 侧栏已隐藏（333）、页面文件已删，它的「全量消息」能力变成本页「数据范围：全部消息」。待办档 = `handle_status=0` 的消息 + `PENDING` 流程（两类各取 200 条内存合并）；全部消息档 = 消息全量（含已读、通知型、已处理），只走消息表、后端分页。Header 抽屉保留快捷处理，属「提醒入口」，不算第二个办理台。

**查询条件（同一张表，不再分页签）**：数据范围 `待办 / 全部消息`；来源 `流程待办 / 各消息业务类型`（下拉由 `lib/messageCatalog` 的 `MESSAGE_TYPE_OPTIONS` 驱动，21+ 类：危急值、听班呼叫、急诊候诊超时、检查报告…）；关键字；全部消息档另有阅读状态。

**处置按来源分派**：消息 → `MessageProcessDialog`，组件内按 `bizType` 各成一页 —— 危急值（确认接收→填处置措施闭环）、听班呼叫 / 超时升级（到岗应答）、检查报告 / 检验报告（结构化详情）、会诊（跳会诊管理）；其余**消息一律配落地页**：`lib/messageCatalog.js` 的 `GOTO_TARGETS` 集中一张表（与 `BizTypeEnum` 一一对应），弹框按它渲染「前往…处理」（待办型）或「前往…查看」（通知型）。急诊候诊/留观/交班/级别上调 → 急诊医生工作站，分诊复评 → 分诊工作站，全院协调 → 总值班日志，签名待办 → 签名证书，待发药 → 药房发药，报告 → 检查/检验工作站，病历/病案类 → 病案管理或病历质控，欠费 → 欠费管控，医保结算 → 医保结算清单，传染病报卡 → 我的未报，死亡证明 → 死亡证明登记。只有弹框内已闭环的（危急值、听班呼叫）和系统公告不配落地页。新增 bizType 时必须同步这张表，否则弹框又退回只显示正文。

**深链定位（只跳路径 = 落到模块首页，用户还得自己翻）**：表里每条还带 `bizNoKey`（payload 中代表业务单号的字段，如 `emergencyNo`/`admissionNo`/`recordNo`），跳转统一拼成 `/xxx?from=msg&bizType=&bizId=&bizNo=`。解析在 `lib/msgDeeplink.js`（`msgDeeplinkOf` / `pickRowByDeeplink`）。目标页分三档：① **真实定位**——急诊医生工作站按急诊号选中患者、分诊工作站按急诊号预填并选中候诊行、病案借阅/编码任务池/处方审核/收费台按单号筛出那一条；② **聚合页按类型选 tab**——检查/检验/病案三个合并入口按 `bizType` 直接落到对应 tab，且任一 tab 权限都没有时给权限说明，不再白屏；③ **提示条兜底**——`components/his/MsgDeeplinkBar.vue` 挂在 DashboardLayout，所有目标页顶部都会显示「来自统一待办 · <类型> · 单号 X」，页面自身没有对应单号搜索字段时就靠它指明看哪条。新增落地页优先走 ①，做不到再退回 ③。流程 → `FlowTaskHandleEdit`（通过/驳回）。已处理 / 通知型行只给「查看」（同一弹框的只读态）。

入口：工作台消息卡片「查看全部」按 `isTodo` 跳 `/todos` 或 `/todos?scope=ALL`；`/messages` 老链接在路由里重定向到 `/todos?scope=ALL`，页面文件不再单独维护（避免两套消息列表实现漂移）。

**这是查询层聚合，底层两张表一张不动**（不建聚合表、不搬数据、不合并状态机）。落地是前端合并：

- 两个来源各调既有接口（`/system/message/listPage?handleStatus=0`、`/workflow/runtime/listMyTasks`），各取满 200 条（`PageParam` 上限），在页面内存里按时间倒序合并 + 前端分页。
- 待办是「当下要办的事」，量级几十条；超过 200 条该加工商/加催办，不宜靠假分页掩盖。
- 要做到真分页 / 跨模块聚合，再在 `his-core-spi` 加取数端口（`his-ms-workflow` 侧实现），由表的宿主模块聚合——那是下一步，不是现在。
- 权限：页面行 `permission` 留空（权限码只落按钮行）；页面可见 = 角色有没有被授 29654 这条菜单。菜单见 `docs/03-增量SQL变更/329-统一待办（聚合消息与流程待办）.sql`（只授 role 1）、`331-消息待办改名消息中心与统一待办授权.sql`（给持有 `workflow:task:handle` 的角色补授）、`332-统一待办授权到全体员工角色.sql`（持有 102 的员工角色全部补授，患者 19 除外）、`333-消息中心并入统一待办（侧栏隐藏）.sql`（102 置 `is_visible=0`，menu 行/2001 权限码/33 个角色授权都不动 —— 沿用 sql/191、311 的合并先例）、`335-门户入口菜单授权补齐.sql`（门户三入口 101 / 29605 / 29654 铺到 35 个启用角色）。**门户入口区（工作台 / 统一待办 / 急诊值班）不走角色授权**：`SysMenuServiceImpl#mergeWithPortalEntries` 把门户(100)下 `is_visible=1` 的可见菜单无条件并入 `userMenus`，只补可见且启用的行（隐藏的 102 不会被复活）；335 只是把数据补齐让「角色管理」勾选状态与运行一致，新增角色不跑 SQL 也能看见这三项。

设计器里的流程定义、统一待办页（含全部消息视图）共用同一批后端接口，没有新增后端接口。

接口封装：`src/api/workflow.js`（`import request from './request'`，返回 `{code,message,data}`）。
