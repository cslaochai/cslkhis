## 一、结论先说

**原始遥测不落库**。71 台设备 17 条/秒 = **147 万条/天**，全存一年 5.4 亿行、60~80 GB 数据加两三倍索引，任何曲线查询都是扫表。

落库的只有三样东西：**设备档案、事件、5 分钟聚合**；另外冷链按 GSP 口径单独留 5 年归档（按 5 分钟窗口落平均/最低/最高/点数，见第 6 节）。合计约 **2.5 GB/年**（含索引），MySQL 单实例毫无压力。

| 数据 | 落点 | 保留 |
|---|---|---|
| 最新一帧遥测 | Redis `iot:dev:{no}:latest`，TTL 120s | 覆盖写 |
| 最近 60 个点（页面火花线） | Redis `iot:dev:{no}:ring`（List，LTRIM 60） | 覆盖写 |
| 设备在线状态 | Redis Set + `biz_iot_device.online/last_seen` | 71 行，不增长 |
| 事件（告警/取药/开关门/任务） | `biz_iot_event` | 12 个月 |
| 遥测原始点位（B 档） | `iot_raw`（TDengine，一类设备一张超级表） | **90 天** |
| 遥测趋势（B 档） | `iot_agg.st_metric_5m`（TDengine） | **730 天** |
| 冷链温度（GSP 记录） | `biz_coldchain_temp_log` | **5 年** |
| 指令下发 | `biz_iot_cmd_log` | 24 个月 |

## 二、数据量测算

按当前 71 台设备（冷柜 6 / 输液泵 10 / 信标 12 / 环境 4 / 气体 6 / 床垫 8 / 透析 4 / 药柜 3 / 腕带 4 / 消毒机 4 / 机器人 10）：

| 表 | 计算方式 | 行/天 | 行/年 | 估算体积/年 |
|---|---|---|---|---|
| `biz_iot_event` | 演示实测 0.2 条/秒，按真实节奏取 8k | 8,000 | 292 万 | ≈ 1.0 GB |
| `biz_coldchain_temp_log` | 6 台 × 288 条（5 分钟一条） | 1,728 | 63 万 | ≈ 0.18 GB |
| `biz_iot_device` | 设备档案 | — | 71 | 忽略 |
| `biz_iot_cmd_log` | 人工下发，量极小 | — | 千级 | 忽略 |
| `iot_raw`（TDengine） | 17 条/秒，压缩约 10:1 | **147 万** | 5.4 亿 | **≈ 3 GB（90 天内约 1 GB 常驻）** |
| `iot_agg`（TDengine） | 71 × 288 窗口 | 20,448 | 746 万 | ≈ 1 GB（两年） |

扩容台阶：

- **300 台**：TDengine 原始约 1.4 亿点/天（压缩后 ~5 GB/天量级前先调 `DURATION`），聚合 8.6 万行/天；MySQL 侧只增事件，结构不变。
- **1000 台**：原始 14 亿点/天，`iot_raw` 保留期压到 30 天；聚合窗口从 5 分钟放到 15 分钟（行数 1/3）。此时单机 TDengine 仍够，再往上才考虑多副本/集群。

## 三、五张在用表 + 一张 GSP 归档表（已启用）

### 1. `biz_iot_device` —— 设备档案 + 在线影子

- `device_no` 唯一（带 `del_flag`），就是 MQTT 主题里的 `{id}`
- `online / last_seen / last_state / alarm_flag` 是**影子字段**，由接入层批量刷新，业务只读
- `bind_type + bind_id` 已清空停用：绑定关系改由 `biz_iot_device_bind` 承载（一台设备可能先后挂多个患者，档案表只留"它是谁"）
- `enabled=0` 的设备**一律不参与离线告警**——这是 retained `OFFLINE` 假离线唯一的解法

### 2. `biz_iot_event` —— 事件全存（月分区）

- 幂等键 `UNIQUE(device_no, seq, ts)`：设备重连会重发未确认报文，靠它去重
- `handled_flag / handle_by / handle_time / handle_remark` 是告警闭环四件套，护士站"已处理"留痕
- `data_json` 存事件明细（如药柜 `{"drug":"芬太尼注射液 2ml","qty":2}`）
- 分区键 `ts` 必须进主键与唯一键，MySQL 硬约束

### 3. `biz_iot_metric_5m` —— 趋势聚合（B 档停用）

> B 档已把原始点位与聚合都放到 TDengine（`iot_raw` / `iot_agg`），这张表只在 A 档（纯 MySQL）部署时启用；DDL 保留，业务代码不要再写它。

- 唯一键 `(device_no, window_start)`，窗口对齐 `:00 :05 :10`
- 只把**高频查询**的量提成列：`temp`、`rate`、`battery`；其余（跨膜压、压差、RSSI、药柜库存）进 `metrics_json`
- 写入时同时存均值与极值，避免"曲线看不见尖峰"

### 4. `biz_iot_cmd_log` —— 指令审计

- `UNIQUE(device_no, request_id)` 防止重复下发
- `operator_id / operator_name / reason` 必填，对应"远程调速必须有人负责"的口径；AGENTS 禁止 `system` 占位，定时任务确实要下发时用带能力的常量（如 `system:iotGateway`），并在代码注释写明

### 5. `biz_iot_device_bind` —— 设备与住院患者（admission_id）的绑定

- 绑定对象是**住院就诊**（`admission_id`），不是床位：患者转床不用重绑，泵跟着人走
- `bed_no/ward_name/dept_name` 只是绑定时快照，方便页面直接渲染，权威仍在住院域
- `bind_source` 1-扫码 2-手工 3-共享调配；`unbind_time/unbind_reason/bind_status` 让解绑可追溯，行不删
- 演示口径：护士扫泵身条码 + 选在院患者；`his/iot/{type}/{id}/telemetry` 里的 `deviceId` 靠这张表反查患者

### 6. `biz_coldchain_temp_log` —— GSP 5 年归档（已启用，2026-11-25）

- 建表：`docs/03-增量SQL变更/366-冷链GSP留档表（补建·最低最高温与点数）.sql`；`UNIQUE(device_no, ts)`，按年分区
  `p2026/p2027/p2028/pmax`，保存 **5 年**
- 归档口径：固定 **5 分钟**窗口（比 GSP「储存期 30 分钟记一条」更细），每窗一行，落 `AVG(temp)`、`MIN/MAX(temp)`、
  `AVG(humidity)`、`point_count`；只归档已走完的窗口（end = 当前时间向下取整 5 分钟再减 5 分钟）
- 写入方：`ColdChainArchiveTask`（`initialDelay=60s, fixedDelay=10min`）→ `ColdChainArchiveService`；游标 =
  归档表 `MAX(ts) + 5 分钟`，首次回补 24 小时、最多回补 7 天，批量 `INSERT IGNORE` 天然去重
- 查询方：`/iot/telemetry/coldChainRecords` 把 TDengine 实时 5 分钟聚合与归档表按 `ts` 合并（实时优先、归档补历史）。
  **导出不再受 TDengine 90 天保留期限制**，90 天以前的历史从归档表读
- 首次归档实测（2026-11-25 18:15）：580 行，`min_ts=10:05`、`max_ts=18:10`；FRIDGE-01 当日 99 行、无重复 ts

## 四、写入链路（关键在"批量"）

```
MQTT 订阅线程（单连接）
  ├ 解析报文 → Redis HSET latest + LPUSH ring/LTRIM（不落库）
  ├ 事件 → 内存队列 → 每 1 秒或满 200 条 → INSERT IGNORE 批量入 biz_iot_event
  ├ 遥测 → 按类型映射成列 → 每 200~500 行批量 INSERT iot_raw.st_*（TDengine）
  │        └ 5 分钟窗口到期 → 批量 INSERT iot_agg.st_metric_5m（TDengine）
  ├ 冷链温度 → 页面/导出按需从 TDengine 做 5 分钟聚合；5 年归档表待建（见第 6 节）
  └ 状态变化 → 只更新 Redis；online/last_seen 每 30 秒批量 UPDATE 一次
```

三条必须守住的：

1. **`last_seen` 不能逐条 update**。17 次/秒 × 71 台 = 每秒上百次行更新，InnoDB 行锁和 redo 全耗在这；30 秒批量刷一次，误差在半分钟内。
2. **离线判定在接入层做，不靠 SQL 算**：`last_seen` 超 3 分钟且 `enabled=1` 才置 `online=0` 并补一条 `OFFLINE` 事件；同一台设备一次离线只写一条，避免抖动刷屏。
3. **先 Redis 后落库**。Redis 写失败不影响业务看板，落库失败由队列重试；反过来会让页面跟着库一起卡。

Redis 键规划：

| 键 | 类型 | 用途 | TTL |
|---|---|---|---|
| `iot:dev:{no}:latest` | Hash | 最新一帧 metrics + state | 120s（靠 TTL 自然过期即可判离线） |
| `iot:dev:{no}:ring` | List | 最近 60 点，页面火花线 | 覆盖 |
| `iot:online` | Set | 当前在线设备编号 | 覆盖 |
| `iot:alarm:{deptId}` | ZSet | 科室未处理告警（score=ts） | 处理即移除 |

## 五、保留策略与分区维护

| 表 | 保留 | 清理方式 |
|---|---|---|
| `biz_iot_event` | 12 个月 | `DROP PARTITION` |
| `biz_iot_metric_5m` | **B 档停用**（A 档才用，30 天） | `DROP PARTITION` |
| `iot_raw`（TDengine） | 90 天 | 库级 `KEEP 90`，自动清理 |
| `iot_agg`（TDengine） | 730 天 | 库级 `KEEP 730`，自动清理 |
| `biz_coldchain_temp_log` | **5 年**（GSP：记录及凭证至少保存 5 年） | `DROP PARTITION`（按年分区） |
| `biz_iot_cmd_log` | 24 个月 | 按 `send_time` 批量删（量小） |
| `biz_iot_device` | 永久 | 软删 |

**禁止 `DELETE` 千万行表**：会长时间锁表、binlog 暴涨，业务查询直接超时。

每月 25 号前把下个月的分区补出来（`REORGANIZE pmax`），同时 drop 过期分区：

```sql
-- 补下个月
ALTER TABLE biz_iot_metric_5m REORGANIZE PARTITION pmax INTO (
  PARTITION p202702 VALUES LESS THAN ('2027-03-01'),
  PARTITION pmax VALUES LESS THAN (MAXVALUE));
-- 丢过期
ALTER TABLE biz_iot_metric_5m DROP PARTITION p202701;
```

默认建到 `pmax (MAXVALUE)` 是为了**写入永不失败**：忘了补分区只是数据全落进 `pmax`，不会报错；但 `pmax` 太大后 `REORGANIZE` 会很慢，所以还是要按时维护。MySQL 单表上限 8192 个分区，按月分 30 年也用不完。

## 七、扩展方式

- **加设备类型**：只加 `device_type` 码值，五张表结构不动；模拟器侧加配置即可，HIS 侧不用改表。
- **加指标**：先塞 `metrics_json`；只有被列表/筛选/告警规则用到的量才提成列（提列要同步改 index 与 VO，属于要单独拍板的一步）。
- **不建 11 张设备表**：11 类设备的字段 80% 重复，加第 12 类又得建表；统一三张 + 业务专属原始表（冷链/透析/消毒各自留档）才是可持续的形态。
- 分区表**不能建外键**，`device_no` 的引用完整性由接入层保证（档案里没有的编号直接丢弃并告警，不写事件表）。

## 八、厂商实际是怎么存的

查了输液、冷链、大型三甲和云厂商四类落地案例，没有一家把设备原始报文直接写进 HIS 的业务库。

| 场景 | 厂商做法 | 关键结论 |
|---|---|---|
| 智能输液（厂商 A） | 设备 → 蓝牙/LoRa 物联网中枢 → **厂商自带的"闭环输液服务器"**（应用 + MySQL + 告警引擎）→ 护士站大屏；与 HIS 之间走 HTTP 双向同步病区/患者/医嘱与告警 | HIS 里只存**输液记录级**数据：开始/结束时间、输入量、报警次数、响应时间；每秒滴速只在服务器内存和大屏上活，不落业务库 |
| 药品冷链 | 测点终端 → 管理主机 → 冷链监控软件（自带库）；法规强制"数据不可更改、不可删除、不得反向导入" | 采样按 GSP：**每分钟更新、储存期 30 分钟记一条、超限时 2 分钟记一条**；记录与凭证至少留 **5 年** |
| 大型三甲（解放军总医院，263 台设备） | 云—边—端：边缘侧做流接入与缓存，云侧数据湖 + 应用层；4 年累计 **24.07 TB**，接入吞吐 23.91 MB/s | 存储大头是监护仪波形/高频信号，**这类数据只进数据湖，不进 OLTP**；业务库只留事件与结论 |
| 云厂商参考架构（AWS × 儿童医院） | HL7 MLLP → Kinesis → Flink 解析 → **Timestream 时序库**；同时原始 JSON 进 S3 数据湖，分析进 Redshift | 元数据、时序、原始报文**三条存储链路分开**，各用各的引擎 |
| 通用 IoT（TDengine / IoTDB / InfluxDB） | 一台设备一张子表（超级表 + 标签），列存 + 时间分区 + 压缩（10:1 以上），热数据本地、冷数据对象存储 | 设备数上万、秒级采样时才划算；71 台用它是"为 1% 的负载买一套集群" |

共同规律五条：

1. **元数据/配置 与 时序 分开**：设备档案、床位绑定这类关系数据放关系库，采样值放时序引擎。
2. **原始报文进对象存储**，按天压缩归档，谁要追溯谁去取，不占业务库。
3. **HIS 不直连设备**：中间一定有厂商网关或集成平台，HIS 只对接网关的 HTTP/HL7/消息接口。
4. **业务库只存"结论级"数据**：事件、告警、治疗/输液记录；过程量只做实时展示。
5. **合规数据单独一条链路**：不可改、不可删、按年归档，和运营数据物理隔离。

## 九、我们取哪一档

| 档位 | 适用条件 | 存储组合 |
|---|---|---|
| **A（轻量备选）** | ≤300 台、无波形、采样 ≥1 秒，且不想多养一个库 | **MySQL + Redis**：Redis 存最新值/火花线，MySQL 存档案/事件/5 分钟聚合/合规记录 |
| **B（当前已落地）** | 需要秒级历史曲线，或设备数往上走 | MySQL（档案/事件/指令审计）+ **TDengine 3.3**（`iot_raw` 90 天 + `iot_agg` 730 天）+ Redis；`biz_iot_metric_5m` 停用 |
| C | 接监护仪波形、影像、内镜视频 | 边缘网关本地缓存 + **MinIO/S3 对象存储**（原始报文/波形）+ 时序库存趋势 + MySQL 存业务 |

现在是 A 档，71 台 17 条/秒对 MySQL 来说是很轻的负载。但代码里要把**聚合写入收口成一个端口**（`IotMetricSink`，MySQL 实现 / TDengine 实现两版），切 B 档时只换实现，业务代码和页面不动。132 上已有 MinIO（milvus 在用），将来上 C 档可以直接复用，不用再装。

## 十、还没定、需要你拍板的两点

1. `biz_iot_device` 是否直接挂在 `sys_equipment` 上：现在设备档案是独立表，如果设备科要求"一个台账管所有资产"，就得二选一——`sys_equipment` 加 `iot_device_no` 外键列，或 `biz_iot_device` 反向引用 `equipment_id`。
2. 冷链按 GSP 留 5 年已写进设计，但你们药房如果执行更严的院内制度（有医院要求 5 年以上或随货留档），要确认后再定分区数量；另外"不可改删"意味着这张表**只允许 INSERT**，不允许 UPDATE/DELETE，代码评审要卡这一条。
