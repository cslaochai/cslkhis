# HIS 质控体系全景（行业口径调研）

> **先给结论**：HIS 里的"质控"**不是一个模块，而是散在 8~10 个业务子系统里的一批规则点**。
> 问"HIS 有哪些质控"，答案取决于你用哪个维度切：
>
> | 维度 | 分法 | 用途 |
> |---|---|---|
> | **时间** | 基础质量 / 环节质量 / 终末质量（≈ 事前 / 事中 / 事后） | 讲体系、讲考核权重 |
> | **组织** | 院、科两级（国家规定）→ 三级 / 四级质控网络（医院实践） | 讲责任、讲谁签字 |
> | **性质** | 硬阻断 / 软提示 / 事后指标 | **写代码时唯一有用的分法** |
>
> 本文件按"业务域 → 质控点 → 性质"拆，末节给"一个质控点该写进哪个文档"的落位规则。
> 与本目录 `HIS流程闭环全景-行业口径.md` 配套：那篇讲**流程闭环**，这篇讲**质量规则点**，两者不是一回事。

## 0 三个维度先说清，避免"三级质控"这种词被混用

### 0.1 时间维度：基础 / 环节 / 终末

行业教材的标准三段，也是医院内部考核的分配口径：

| 层 | 内容 | 典型考核权重 |
|---|---|---|
| **基础质量** | 人员资质、设备状态、药品与耗材安全、环境设施 | 约 15% |
| **环节质量** | 诊疗过程中的关键节点：接诊、住院诊疗、手术、用药、院感、危急值 | 约 65%（重心） |
| **终末质量** | 病案质量、疗效评价、满意度、平均住院日、病死率、再入院率 | 约 20% |

> 权重示例出自某院临床科室质量管理架构（基础 15% / 环节 65% / 终末 20%），各家数值不同，但"环节占大头"是共性。

**事前 / 事中 / 事后**是同一套东西在信息系统里的叫法：
- 事前：开立/提交前的校验（拦截）
- 事中：诊疗进行中的实时提示与预审核
- 事后：出院/结算后抽检、疑点分析、指标统计

### 0.2 组织维度：两级是法定，三级是实践

- **法定口径**：《医疗质量管理办法》第九条——医疗质量管理实行**院、科两级责任制**；主要负责人是第一责任人，业务科室主任是本科室第一责任人；二级以上医院设医疗质量管理委员会。
- **实践口径（病案三级管理制度）**：
  1. **一级**：病房主治医师/质控医师逐份检查出院病案（书写格式、病程分析、三级查房、诊断依据、医嘱单），科主任审签；护士长查护理记录。
  2. **二级**：病案室（科）质控人员**每天**检查已出院病案，把缺漏项、错误反馈给临床，限时补正。
  3. **三级**：医务科组织病案质量检查组，**至少每季度**抽查在院病案、出院病案和门诊病案，总结问题、监督整改。
- **四级网络**（部分医院）：质控医师/护师/技师（一级自控互控）→ 科室质控小组（科主任、护士长、医疗组长）→ 职能科室（医务/护理/院感/药事）→ 院级质量管理委员会。

> ⚠ "三级质控"在不同语境下指三件不同的事：①医疗质量三级管理体系（科室/院级/外部）；②病案质控三级（医师/病案室/医务科）；③医保清单质控的两段（院内前置/医保端后置）。**它不是一套规则集**，讨论时必须先说清指哪个。

### 0.3 性质维度：硬阻断 / 软提示 / 事后指标（实现时的关键一刀）

这三类的实现方式完全不同，混着做必然做废：

| 性质 | 判据 | 实现方式 | 典型例子 |
|---|---|---|---|
| **硬阻断（H）** | 规则确定、能用码值或阈值表达，对错无争议 | 同步校验，挡在提交动作之前；或 409 二次确认 | 必填项缺失、书写超时、性别—诊断冲突、超限收费、抗菌药物越级、输血申请超量、上传字段不合规 |
| **软提示（S）** | 需要人判断，存在合理例外 | 异步计算、给人看、**允许申诉、不计扣分** | 病历内涵一致性、编码合理性、DRG 入组合理性、医保证据是否充分、用药适应证 |
| **事后指标（M）** | 拦不住，只能评价 | 报表 / 看板 / 上报 | 入组率、CMI、病死率、再入院率、平均住院日、处方点评合格率、手卫生依从性 |

> 这条分法直接对应行业实证：AI 擅长的恰恰是 S 类，而 S 类在真实医院里**申诉率是核心指标**（某院上线内涵质控助手后申诉率 7.42%→3.42%、误报率 5.30%→1.982%）。**AI 发现如果直接计扣分，申诉量立刻反弹。**

## 2 机制：行业是同一套流水线

无论哪一域，机制都是这六段，区别只在规则来源：

```
规则库（多部门共建、可动态维护）
   → 规则引擎（校验/打分）
   → 结构化预警（问题类型 + 违反条款 + 涉及数据项 + 证据原文）
   → 推送给具体责任人（医师/护士/编码员/医保审核员）
   → 人工复核（确认属实 / 申诉 / 驳回）
   → 整改闭环 + 指标看板
```

几个关键工程口径：

1. **规则库必须由多部门共建**（医保、医务、药学、病案、信息、临床），且随政策/本地分组调整而更新；靠信息科单方面维护的规则库必然过期。
2. **预警必须结构化**：只给一句"有问题"，复核人无法处理；要给规则条款号、字段、原文证据。
3. **分级不是模型定**：严重度（提示/重要/否决）由规则或评分算出来，模型只负责组织语言。
4. **能拦的往前拦**：行业明确要求把上传类校验"嵌入填报时点"，违规不允许提交；事后才发现，账已经结出去了。
5. **不拦的要能申诉**：S 类误报会消耗临床信任，申诉率是衡量质控系统是否可用的第一指标。

| 本系统要覆盖哪些质控点、优先级、验收标准 | **需求规格说明书**（`00-开发文档/101`） | 一条一句"系统应能……"，带验收判据 |
| 某质控点的表结构、接口、规则码、类归属 | **详细设计说明书**（`00-开发文档/101-详细设计`） | 落到具体模块的 `xxxQcRule` / 接口 / 表列 |
| 跨模块的质控流程、状态机、时序 | **`12-部分流程图/`** 的流程图（HTML/Mermaid） | 画节点、分支、人工闸 |
| 质控指标口径、计算方式、上报口径 | **需求规格 + 指标口径附录** | 公式、分子分母、统计周期 |

**建议的推进顺序**：
1. 用本文件做**基线对照表**，逐条标"已覆盖 / 部分覆盖 / 未覆盖"（这一步只做标记，不改代码）。
2. 只把"未覆盖且属 H 类"的进需求规格，因为 H 类是必须拦的。
3. S 类进详细设计时，明确写清"是否计扣分、是否允许申诉、模型不可用时降级成什么"——这三条不写清，做出来一定被临床抵触。
4. M 类只进报表清单，永远不要试图做成流程拦截。
