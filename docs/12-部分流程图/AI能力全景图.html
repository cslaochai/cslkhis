1. 全局分层 Layered Architecture

所有模型调用（除语音转写外）都收敛到同一个执行器 AiExecutionServiceImpl，能力层只负责「取业务事实 + 拼提示词 + 决定降级成什么」。

2. 统一执行链路 Common Pipeline

每个能力把自己的业务事实渲染成提示词，然后只关心一件事：拿到强类型结果，或者拿不到时该回落成什么。

能力层组装 AiCallDTO

capabilityKey · templateName · 提示词变量 · bizType/bizId · 输入摘要（脱敏）

例：drug_audit 传处方+药品+过敏史；icd10 传病历四要素 + 召回候选集

闸一：能力开关

aiConfigProvider.isCapabilityEnabled(key) —— 关掉的能力直接不产生任何模型请求

闸二：熔断守卫

连续失败 5 次 → 该能力冷却 300 秒；冷却后半开放行一次试探

渲染提示词（取生效版本）

PromptTemplate.render(templateName, variables) —— 模板存库、带版本号，可回退

调用模型

jsonMode=true · 按能力配模型 / lite 模型 · 独立超时 · maxTokens 上限

强类型解析

抠 JSON（兼容代码块包裹）→ 反序列化到能力自己的 XxxLlmOutputDTO

解析成功

记成功 + 落审计

清熔断计数 → sys_ai_call_log：模型 / 提示词版本 / 耗时 / prompt+completion tokens / 输出摘要

返回 Optional.of(result)

能力层拿到强类型结果，继续做业务合并

解析失败

自纠重试一次

把「你上次不是合法 JSON，报错是 X」回灌，要求只输出 JSON，再调一次

降级：Optional.empty()

记 FAILED / TIMEOUT + 失败原因 → 能力层回落成确定性结果，并把可运维的原因带回前端

为什么降级原因要一路带回前端：「AI 不可用」对医生没有价值；「密钥未配置 / 已触发熔断 / 模型服务不可达」才能指向修配置或找运维。

3. 五条调用形态 Five Shapes

每个能力都属于下面五种形态之一。判断「AI 在哪一步说错话」时，先定位它属于哪种形态。

3.1 规则优先 + 模型补位（临床判定类）

确定性层：取事实 + 算规则

生命体征 / 处方明细 / 病历字段 / 检验结果 → 硬规则或评分

是否需要模型？

按阈值判断：未达阈值不调模型（省成本，也避免模型把正常说成异常）

模型层：只补长尾

模型输出必须落在确定性层能解释的范围内（候选集内 / 只升不降 / 只做建议）

合并输出（确定性结论优先）

硬规则给出的「不通过 / 级别 / 分值」不可被模型改写

处方审核 drug_audit

硬规则先跑（剂量、重复、相互作用）→ 模型补 ≤5 条长尾 → 去重排序。pass 只可能被硬规则 BLOCK 否决

急诊分诊 emergency_triage

生命体征红旗 + 主诉关键词定级 → 模型给建议级别/绿通/话术 → 合并只升不降；模型新报的红旗只展示、不参与定级。

检验解读 lab_interpret

规则层先出异常/危急值/未判定计数与趋势 → 异常项达阈值才调模型做连贯解读 → 否则规则结论（这不算降级）。

病情恶化预警 deterioration_alert

评分规则算分定级（近 24h 体征）→ 未达预警阈值不调模型 → 达阈值才请模型写处置建议。

病历质控 emr_qc

必填项 + 占位符判定（「无」「未见异常」不算已填）→ 模型查内涵问题 → 降级仍返回规则问题。

ICD-10 编码 icd10

先召回候选集 → 模型只能在候选集内挑选 → 模型给出的码不在候选集 = 幻觉被拦，按召回分回落。

3.2 受控 SQL 问数（operation_qa）

表白名单（fail-closed）

从「问数配置」查启用表；配置为空 = 什么都不让查，直接拒绝

选表 + 语义命中

先按问题挑相关表，只把相关 schema / 语义 / 敏感规则 / 表关系注入生成段

模型生成单条 SELECT

输出契约：标题 + SQL；非统计类问题返回空 SQL = 主动拒答

SQL 闸门（5 道）

只读且单语句 · 禁注释 · 关键字黑名单 · 禁跨库 · 表名白名单 · 强制 LIMIT 200

敏感列第二道防线

标记「禁止出库」的列出现在 SELECT 中 → 直接拒绝（提示词约束之外的硬校验）

执行 + 结果脱敏

行数上限兜底；按「结果列 → 源列」映射在后端打码

可选：模型总结

总结失败静默置空，表格照常返回

设计要点：模型的产物是一段文本 SQL，所以它必须先经过与「人写 SQL」完全相同的安全闸门才能执行；拒绝路径给的是可读原因，而不是 500。

5. 知识库管线 RAG Pipeline

问答只是后半段；真正决定回答准确率的是前半段的「切块、向量化、版本」。

录入

文档上传 / 批量导入 / 手工录入（含分类、版本、来源）

解析 DocumentParser

按文件名分派解析器，异步线程池执行，任务状态可查

切块 TextSplitter

chunkSize / chunkOverlap 可配，参数会被评测快照记录

向量化

本地 TF 或远程 Embedding，由选择器按配置切换

写入向量库

Milvus / 内存实现；文档版本历史可回退；支持全量 rebuild 与单文档重建

问答 / 评测共用检索

同一套 embedding + topK 参数，保证「评测通过」和「线上表现」是同一件事

版本与重建：文档有 sys_knowledge_doc_history 可回退；重建走任务化（进度可查），避免大文档卡住请求线程。

6. 评测与可观测闭环 Evaluation & Observability

四条数据流：离线评测证明「没退化」，在线日志发现「现场失真」，调用审计定位「哪一环坏了」，提示词版本支持「回退」。

① 离线评测（检索层）

评测用例（问题 + 期望文档）→ 运行 → recall@k / MRR / 平均耗时；每次 run 存 chunk 参数与 embedding 提供方快照，明细保留命中位次。

② 在线观测（问答）

sys_knowledge_query_log：问题、回答、命中文档、是否降级、降级原因、耗时、顶/踩反馈。

③ 调用审计（全部能力）

sys_ai_call_log：能力、模型、提示词版本、状态（成功/超时/失败/降级/熔断）、耗时、token、输入输出摘要。

④ 健康与开关

逐能力的启用状态、熔断状态、累计降级次数；提示词按版本生效、可一键回退。

反馈与 badcase

顶踩 / 审计日志里的失败与降级 / 医生对草稿的修改

沉淀为评测用例

每条 badcase 补进 sys_knowledge_eval_case（或对应能力的评测集）

改动前跑基线

改提示词 / 换模型 / 调 chunk 参数

同集对比 → 上线或回退

评测集版本 + 提示词版本 + 模型名 + 参数快照一起留痕

当前边界：这套闭环目前只覆盖知识库的检索层（recall@k / MRR），回答正确性没有自动评测；全仓 src/test 为 0 个用例，评测靠管理台手工触发，没有 CI 回归。

7. 现状短板与断链 Known Gaps

  • 评测只到检索层。能证明「没找错材料」，不能证明「答对了」；回答层缺引用支撑率、字段级 F1 等指标。
  • 无自动化回归。后端测试目录为空，提示词/模型变更前后只能人工比对。
  • 三个能力后端就绪、前端无入口。处方审核（drug_audit）、病历质控（emr_qc）、预问诊摘要（previsit_summary）。
  • 一处前端断链。小程序调用 /ai/patient/medicationGuide，后端未实现（404）。
  • 缺少「采纳率 / 修改率」埋点。草稿类能力只有顶踩（1 bit），没有「生成 N 字、最终保存改了多少字」的连续指标。
  • 回答未强制逐句引用。知识问答返回 sources 列表，但未要求模型逐句标注依据，无法直接计算引用支撑率。
  • 命名与实质不一致。患者费用解释挂在 AI 能力包里，实为纯规则实现。
