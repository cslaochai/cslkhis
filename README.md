# CSLK-HIS · 三甲医院信息化系统（Hospital Information System）

一套面向三甲医院业务闭环的全栈 HIS 系统：模块化单体后端 + Vue3 管理端 +
微信患者端小程序，覆盖预约挂号与全院排班（人力出勤）、门诊医嘱与电子病历、手术麻醉与日间手术、检验检查（LIS/PACS）、药房药库、收费结算与医保、急诊分诊等临床域，以及患者端互联网服务（智能导诊、预问诊、报告解读、随访、在线客服）和
AI 辅助（ICD-10 编码、处方审核、病历质控/草拟、检验/报告白话解读、运营问数、知识库 RAG 等 18 项能力）。

## 快速开始

### 前置要求

- JDK 21+、Maven 3.9+
- MySQL 8.0+、Redis
- Node.js 20+、pnpm

### 1. 初始化数据库

1. 先执行 `docs/01-初始化DDL/` 下 `01~23` 编号的领域 DDL（全库建表快照，无 DROP、无数据）。
2. 再执行 `docs/02-铺底基础数据/` 的铺底数据（`00_import_all.sql` 汇总导入，或按需单表执行）。
3. 最后按编号顺序执行 `docs/03-增量SQL变更/` 下的增量脚本（排班、AI、患者端服务等新域的结构与菜单授权演进）。

### 2. 启动后端

配置分三层：`application.yml`（环境无关公共配置）、`config/domain/his-*.yml`（领域行为片段，dev/pro 共用、零密钥）、
`application-{dev,pro}.yml`（环境差异）。**密钥一律走 `HIS_*` 环境变量**（数据库、Redis、JWT、签名主密钥、AI 密钥，参照
`docker/.env.example`）；`application-dev.yml` 为本地个人配置，不入库。

```bash
cd source/back_end
mvn clean package -DskipTests
java -jar his-web/target/his-web-1.0.0.jar
# 或 IDE 直接运行 com.his.HisApplication，服务监听 :8080
```

接口文档（Knife4j）：`http://localhost:8080/api/doc.html`

### 3. 启动管理端

```bash
cd source/front
pnpm install
pnpm dev        # 默认 http://localhost:3000
```

dev server 将 `/api` 代理到 `http://localhost:8080`；需要指向其他实例（如另跑一个 jar 做验收）时，用
`VITE_API_TARGET=http://localhost:8082 pnpm dev`，不改配置。

### 4. 患者端小程序

用微信开发者工具导入 `source/miniapp/`，修改 `app.js` 中的 `globalData.baseUrl`（默认指向局域网后端）为你的后端服务地址。

### 5. Docker 部署（可选）

```bash
cp docker/.env.example docker/.env   # 复制后填真值（.env 不入库）
docker compose -f docker/docker-compose.yml up -d --build
# 后端 http://localhost:8009/api  ·  管理端 http://localhost:3100
```

## 架构要点

### 模块化单体（Modular Monolith）
系统采用「单一可部署单元、内部按业务域切分模块」的形态：保留单进程部署、事务一致、调试简单的好处，又通过清晰的模块边界获得接近微服务的内聚与可演进性。它不是分布式微服务，不引入跨进程通信与分布式事务的复杂度。

### 单向依赖与分层
依赖方向严格单向：公共底座在最底层，业务域居中，AI 与互联网医院等横切能力位于业务之上，最后由启动层组装并统一暴露 HTTP。跨域交互一律走对方的「服务」接口，模块之间不直接触碰彼此的数据访问层——从物理层面杜绝循环依赖与隐式耦合。

### 前后端契约
接口风格统一、可预测：以资源为中心的 RESTful 路由，配统一的 `{code, message, data}` 响应壳；入参用带校验的 DTO，出参按用途区分 VO（列表 / 详情 / 下拉）。超长整型主键以字符串形式在前后端之间传递，规避 JS 精度丢失。动词仅保留 GET / POST / DELETE，复杂查询统一走 POST。

### 鉴权与权限模型
登录态基于令牌，权限由菜单数据驱动——同一套权限定义同时约束前端可见性（菜单 / 按钮）与后端方法级可达性，两端各守一道闸。角色 → 菜单 → 按钮的授权可旁路插入，但任何权限变更后必须让缓存失效才能生效。

### 数据字典与枚举的双轨
码值到文案只有两条受控出口：**需要在代码里「基于值做分支」（状态机、校验、统计）的用枚举；只用于展示、从不参与分支的用字典。** 两者各自只在一处定义、一处取用，杜绝「同一个码值在不同地方说法不一致」。

### 电子签名与合规
内置可信时间戳与签名能力，用于病历、处方等需留痕且不可抵赖的业务对象，支撑签名链与验签。签发成功不等于验签通过，改了内容再验签必须失败——二者独立校验，保障合规可追溯。

### AI 能力的接入哲学
AI 不是嵌入业务代码的黑盒，而是一层「横切能力」：业务模块不得依赖 AI 模块，由 AI 层反向读取业务数据来产出候选。核心纪律——**事实必须由确定代码判定，模型只负责解释与生成候选**；任何能力在模型不可用时必须能降级为纯规则 / 人工兜底，且降级对用户可见；全部模型调用经唯一入口并落审计。

### 配置与凭据隔离
代码与配置入库零密钥：环境口令（数据库、缓存、令牌签名、AI 密钥）一律走环境变量，本地差异配置不入库。配置分三层——公共基础、领域行为片段（dev/pro 共用、零密钥）、环境差异，保证不同环境结构一致、仅值不同。

### 数据治理基线
数据库结构以「全量 DDL 快照 + 铺底基础数据 + 编号递增增量脚本」三段式管理，是前后端与验证脚本唯一对齐的数据源。逻辑删除、审计字段、时间截断等跨表约定由统一基类与工具收敛，避免各模块各自造轮子。
